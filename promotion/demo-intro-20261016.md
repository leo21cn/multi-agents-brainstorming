# 我如何从0构建一个自用的多智能体多人类角色的头脑风暴工具

> 火花会 Sparkwave 第一版完整复盘：从"为什么做人机混合头脑风暴"到一次真实讨论的闭环。

## 0. 先说结论

过去一年多，我越来越习惯通过与 LLM 智能体对话获取知识——确实高效。但当我需要"想清楚一件事该怎么做"时，单模型对话很快暴露两个问题：知识边界与立场惯性，它顺着我的问题推演，容易形成回音室；知识来源单一，缺少来自其他行业、其他职能的视角来挑战我的假设。

于是我自己动手做了一个自用工具：**火花会 Sparkwave**——人类成员与多个智能体角色在同一个浏览器群聊房间里围绕命题头脑风暴，人类主持人控制节奏，讨论到阶段生成带来源标注的结构化结论。第一版为单机演示系统，绑定软件工程与项目管理交叉领域。本文按"出发点 → 功能设计 → 技术设计 → 实施过程 → 结果展示"完整复盘。

## 1. 出发点：三个朴素判断

**判断一：与智能体沟通能高效获取知识，但头脑风暴需要多角度。** 单个模型无论多强，都只有一个立场惯性。真正有价值的讨论来自多个专业视角同时在场、互相挑战。这些视角天然对应不同行业与领域的知识、经验——业务、技术、交付、成本、风险、质量。

**判断二：人类不能缺席，且必须握着节奏控制权。** 最终决策的责任在人。我的设计把"何时收敛、何时产出"的控制权留给人类主持人：智能体只能在被点名、被放行或被 @ 提问时发言。

**判断三：视角差异必须设计进数据，而不是写进提示词。** 让八个智能体写八段不同的提示词，得到的大概率是同一模型换八种语气。我的做法是给每个智能体绑定不同的领域知识库（检索增强），让"视角差异可被识别"成为结构保证。

定位是自用：单机、浏览器访问、零部署负担，但功能按真实会议形态做完整——邀请进房、举手插嘴、发言权、阶段结论、记录导出，一样不缺。

## 2. 功能设计：一场"会议"的完整生命周期

系统分三层：管理后台（系统级配置）、房间（一次讨论）、人类成员（经邀请链接进房）。

**系统级配置。** 三个核心实体：模型连接（API 地址、Key、可用模型名列表，统一走 OpenAI 兼容端点）；知识库（三维度固定：业务领域 / 项目管理与软件工程方法论 / 技术架构，文档上传即解析、切分、嵌入、入库）；智能体（选用模型连接与具体模型 + 绑定一个或多个知识库 + 提示词人设/专长/发言风格 + 发言节奏档位）。系统初始化门槛：至少一个知识库 + 一个已绑定知识库的智能体，未达标不允许建房。

内置八个角色：业务领域专家、架构师、交付负责人、一线开发、测试负责人、产品负责人、成本／风险分析师、批判者，各绑不同知识库组合；想覆盖其他行业，只需替换业务领域库语料，机制不变。

**房间与成员。** 建房时填命题（≤200 字）、从系统级智能体中选用阵容、选编排模式（本版完整实现"人类主持控制"，其余三种留接口）。人类成员经邀请链接进房：先落到进房落地页，看清命题、主持人、阵容，填昵称取得连接级身份，此后以该身份发言。非主持人的人类成员与智能体同权——须举手被放行，或被主持人 @。

**讨论编排（核心体验）。**

- **举手插嘴**：每条新发言落定后，系统重判在席智能体的发言意愿——仍想说的原位改写意图，不想说的自行撤回；智能体自主举手、主持人模拟举手、人类成员举手三条来源混排同一条待发言队列，主持人放行或驳回。
- **@ 定向提问**：一条消息可 @ 多位智能体，各受话者按书写次序依次应答；@ 指向人类成员则授予一次发言权。
- **发言权**：非主持人人类成员一次一发、发完即消耗；主持人不限。
- **发言节奏三档**（快闪／均衡／深思）：控制思考开关与正文字数目标，发言流式呈现"检索→思考→生成"三阶段。
- **语音输入**：按住录音，转写文本实时填入输入框、不自动发送。
- **产出**：主持人键入 "/" 触发斜杠技能——生成阶段结论、导出发言记录；生成期间全房间等待并暂停发言。

**阶段结论。** 固定四章——命题、关键观点、分歧点、初步结论／建议，其后 0~10 章由模型按本次讨论的实际内容归纳、章名自拟（如"行动项与负责人""风险"）。关键观点与分歧点逐条带来源标注：界面与文档呈现智能体名，其所绑知识库保留在标注数据中供追溯。发言记录导出逐条带时间与来源。

## 3. 技术设计：五个关键决策

一句话概括：**Python 后端单进程 + 免构建静态前端 + 自研编排 + 三维 RAG + 分层记忆。**

| 层 | 选型 |
|----|------|
| Web | FastAPI（REST + WebSocket + 流式降级端点） |
| 持久化 | SQLite（SQLModel）；本地文件系统存产出 |
| 向量库 | Chroma（嵌入式，无外部服务） |
| 模型 | 系统级模型连接，OpenAI 兼容端点（默认 DashScope/Qwen） |
| 前端 | 原生 HTML/CSS/JS，后端 StaticFiles 同进程托管，第三方仅 markdown-it 单文件 vendor |

**决策一：编排自研，不接外部多智能体框架。** 发言触发只有三个来源——主持人点名、放行举手、@ 受话者次序——全部由接入层直接驱动，不需要任何群聊轮次机制。跨请求共享的三件状态（待发言队列、每房间待发言 FIFO 与在途守卫、发言权集合）做成进程内存态，REST 与 WebSocket 两条通道共读同一份。调度策略以 `SpeakerSelectionStrategy` 接口保留四种编排模式的接入点。诚实说明：依赖清单里声明的 ag2 目前无一行代码导入，它只是未来的替换点（已写进已知缺陷清单）。

**决策二：视角差异 = 知识库绑定，而非提示词包装。** RAG 按智能体绑定库限定检索范围；发言时，检索命中的语料连同命题、共享记忆、提示词一起进上下文。

**决策三：记忆分层与上下文组装。** L1 近期原文 / L2 滚动摘要 / L3 长期召回，按房间隔离；近期原文逐条署名（人类成员按各自显示名，不一律记成主持人）；@ 提问作为"当前焦点"紧随命题注入，由消息标识锚定——同一条提问的多个受话者依次应答时，各自取回同一份焦点，不靠"最后一条消息"猜。

**决策四：流式发言与句界收束。** 正文增量以完整句为粒度下发；超出档位安全界时在句界收束并打截断标记（落库与导出都标注）；思考增量只做界面呈现，不落库、不进上下文。同步模型调用全部在工作线程执行，不阻塞事件循环。

**决策五：结论综合的一次调用 JSON 契约。** 一次模型调用输出 JSON 对象，键序即章节序。踩过一个真实的坑：模型常把中文引号写成半角双引号，导致整份回复非法 JSON——解析失败时先按扁平对象结构给内层引号补转义再解一次。

其余：成员令牌只在进房/认领那一刻返回一次、恒定时间比较校验，WebSocket 握手期验身份；API Key 入库但掩码呈现、不入日志与导出；写操作在服务端只认主持人，界面门控只是第一层。另有**离线演示提供方**：未配 API Key 时以确定性输出跑通全链路，配 `DASHSCOPE_API_KEY` 即切真实模型——语料可模拟，模型接入不模拟。

## 4. 实施过程：文档先行 + 里程碑推进 + 测试兜底

**文档链先行。** 先写七份需求与设计文档再动手：概念需求 → 需求规格（12 个功能需求 FR-1~FR-12）→ 技术架构 → 数据模型 → 视图规格 → 用户故事 → 实施计划。实施计划按 M0~M18 近二十个里程碑、106 个任务拆分，每个任务带验收口径。事后看这是最划算的投入：需求写清楚后，实施几乎变成"照着做"，返工集中在少数真实不确定点。

**里程碑推进。** M0 脚手架 → M1 系统级配置 → M2 检索与记忆 → M3 编排与房间 → M4 结论与导出 → M5 前端 → M6 语料与自动化测试 → M7 本地部署闭环；随后多轮迭代补强（M9~M18）：流式输出与配置热生效、发言正文 Markdown 渲染、@ 定向提问、发言节奏三档与思考呈现、自主举手、举手随讨论刷新、邀请进房与连接级身份、结论固定四章收敛。

**数据准备。** 三维度 8 篇自攥要点语料（业务领域：HR 合规、财务会计；方法论：敏捷 Scrum、估算排期、风险管理；技术架构：十二要素、ADR、技术债），全部来自公开来源并逐条标注许可。

**验证。** pytest 四层测试（unit / integration / e2e / acceptance），覆盖验收标准 A-1~A-22；基准命题集端到端跑通四项指标——来源一致率、标注完整率、越权发言数、导出一致性。每个里程碑以"真实模型 + 浏览器人工核对"收尾。

**两条纪律。** 一是文档与代码同轮同步：任何行为口径的变动，在同一轮改动里同时落 `docs/` 与 `program/`；二是已知缺陷不藏：当前 8 项与既定口径的差距（种子脚本不幂等、房间结束不清空待发言队列等）逐条记在运行手册第 7 节。

## 5. 结果展示：一次真实的头脑风暴

2026 年 10 月 16 日，我用第一版跑了一场演示（完整讨论记录与结论文档的导出见文末附件）。

**命题**：某功能预计延期两周，且版本绑定了一个客户侧合规截止日，应砍范围、加人还是推迟发布？

**场景**（主持人陈默交代）：武汉某政务服务系统项目上线冲刺，企业开办"一窗通办"模块的电子证照跨部门同步子功能，因对接省政务数据共享接口遇到字段适配障碍，已滞后 7 天、预计整体延期两周，距客户侧合规上线截止日仅剩 14 天；总预算 110 万元，子功能挣值 12.8 万元、目前仅完成 30%。三个方案陷入争议：砍范围、加人（约 8 万元人力成本）、推迟发布。

**阵容**：人类·陈默（主持人）+ 产品负责人、成本／风险分析师、交付负责人。

**讨论过程摘录**（16 分钟、8 条消息）：

- 产品负责人率先表态："砍范围，砍的是'实时'这个时效承诺，而不是整个跨部门同步子功能"——实时降 T+1，加人与推迟发布都不选。
- 成本／风险分析师同意砍范围，但刀要落得更深：子功能剩余工作量对应挣值约 8.96 万元，加人边际成本 8 万、投入产出比接近 1:1，且 8 万是确定性支出、产出高度不确定——布鲁克斯定律在这里是工程事实；推迟发布则押上客户年度合规考核失分后的后续合同损失，量级 33 万~110 万元。
- 交付负责人给出转折性判断：字段适配障碍发生在省政务数据共享接口上，主流程的身份核验/企业数据拉取极可能共用同一接口——"砍范围不等于把这个接口问题从关键路径上摘除"；若核验路径独立，主流程剩余工期约 9~11 天、14 天窗口有 3~5 天缓冲；若共用污染路径，砍 T+1 也不救命。
- 产品负责人据此修正落刀方式：刀口不在"实时还是整个子功能"里提前押注，由第二天上午两小时的接口核验决定；同时反对把"向监管确认合规最低定义"设为前置闸门（答复周期不可控），改为并行推进。
- 主持人陈默 @交付负责人："我同意上述结论……请生成本次讨论初步结论。"——人类一句话，把讨论收敛到产出。

**生成的阶段结论文档**（4 固定章 + 6 归纳章，共 10 章）：

1. 命题；2. 关键观点；3. 分歧点；4. 初步结论／建议；5. 砍范围方向的共识与落刀点的分歧；6. 加人与推迟发布被排除的依据；7. 接口核验作为决策前置条件的必要性；8. 合规最低定义不应作为前置闸门；9. 行动项与负责人（4 项）；10. 风险（4 项）。

初步结论一句话：**砍范围，刀口由接口核验结果决定，不提前押注；加人与推迟发布均排除。** 关键观点与分歧点逐条带来源智能体标注，每条都可回溯到提出者。

**三点观察。** 其一，角色差异真实产生了观点差异——产品负责人谈用户感知与价值取舍，成本风险分析师谈敞口与量级，交付负责人谈关键路径与接口依赖，这是不同知识库与立场约束下的实质分歧与互相修正，不是同一模型换三种语气。其二，人类介入点干净利落：开头交代背景、结尾拍板产出，中间靠举手与 @ 把节奏握在手里。其三，结论可追溯，这正是"头脑风暴"区别于"AI 代笔"的地方。

## 6. 小结

第一版从概念需求到本机跑通闭环，代码、文档、测试同步交付。当前局限同样明确：另外三种编排模式只有接口没有实现；按音色区分人类发言人、多人远程实时协作、工具型技能（联网检索、代码执行）都留给下一版。

如果你也想自己做一个，我的三条建议：先写需求再写代码；把"视角差异"设计进数据（知识库绑定）而不是提示词里；以及，让人类保留节奏控制权。
